title: Model Catalog
description: Create a requirements-driven Manual or Agentic deployment and review one configuration before approval.
---

Open **Model Catalog** and choose a model. Search combines with category filters,
ignores case, and requires every search word to match the model metadata.
**Clear filters** resets both filters.

## One workflow, two decision modes

| Mode | Decision rule |
| --- | --- |
| **Manual** | Compare applicable provider/cache combinations using target evidence, mechanism coverage and the displayed objective rules; break remaining ties with fewer accelerators. No LLM is called. |
| **Agentic** | Compare validated candidates against the objective, workload and available evidence. An explicitly selected AI provider can propose and rank candidates; fallback is labelled. |

Both use **deployment goals → build / compare plans → review and edit →
deploy and observe**. Existing deployments,
legacy APIs and previously recorded plans are not deleted.

“More mechanisms” does not mean “maximum parameters” or “best performance”.
Incompatible provider recipes remain alternatives rather than being silently
combined. Mechanisms without verified prerequisites stay **unknown**.

## Choose the target

1. Select a model and choose a ready **Cluster**. Lens generates a deployment name;
   expand **Name and description** to customize it.
2. Select **Model cache storage** containing the ready model. This workflow
   currently requires a registered model cache in both modes.
3. Choose **Manual** or **Agentic**, then **Continue to deployment goals**.

Use **Manage model cache** to download a missing model. Cache status refreshes
while the page is open. See [Model Cache](/user-guide/model-cache) and
[Storage](/user-guide/storage).

The initial context length is the model card's exact `contextLength`, with `4096`
used only when absent. Supported values are `256` through `1048576`; no silent
shortening occurs. Runtime images come from the target hardware profile.
Replicas, TP and runtime parameters are edited after generation, not required as
initial deployment inputs.

## Enter requirements

Both modes use one short form. Confirm **Workload**, **Optimize for**, and whether
requests share a long prompt or document. The defaults are **General chat**,
**More throughput**, and **Do not assume shared content**. These are editable
planning assumptions, not observed traffic. Choose shared content explicitly to
consider reuse-dependent optimizations.

**Advanced settings** is collapsed by default. Suggested request sizes are 1024
input tokens and 256 output tokens, reduced to fit models with a smaller context.
The runtime context itself is unchanged. Clearing token fields leaves them
unspecified; saved plans retain their original values, including unknown evidence.
Load and latency targets are optional, with no fabricated SLO. The resource budget
defaults to current free capacity, and optimization controls default to Automatic.
Hardware inventory and runtime selection come from the backend, not a hardware form.

Manual uses **Generate plan and topology** without an LLM. Agentic uses **Compare
deployment plans**, with an optional **AI provider**. **Built-in planner** does not
call external AI. Its advanced search budget defaults to three retained candidates
(1–10), a 60-minute timeout (1–180 minutes), and no deployment trials.

The accelerator ceiling and required/forbidden mechanisms are enforced by the
backend. Live free capacity remains authoritative. Required mechanisms with
unknown prerequisites, incompatible required combinations or insufficient
resources fail explicitly. A latency target is not considered met merely because
the configuration fits in memory.

The Manual browser retains up to 10 recipe/cache alternatives for source checks
(Agentic defaults to three). Manual compares native CPU KV-cache compositions with baseline, precise routing
and P/D, plus the standalone tiered-cache recipe. These are planning candidates,
not proof that the selected source version supports the combination. CPU cache
is capped at 8 GiB per serving replica and 25% of discovered free host memory
across both P/D roles; unknown memory does not authorize offloading.
The source renderer checks connectors, matching images, pinned revisions and
placement before enabling a planned cache. Sequence count is bounded by the
selected model/VRAM capacity estimate when available.

After target evidence and mechanism coverage, throughput prefers P/D then precise
routing; latency prefers precise routing; cost prefers fewer accelerators;
reliability prefers multiple serving replicas. Remaining ties prefer fewer
accelerators. The selection rationale and alternatives expose this default policy;
it is not a measured latency/throughput claim. Unsupported combinations are not
silently overlaid.

Load-target planning currently uses native AIC recommendations and accepts only
one of concurrency or request rate. Missing compatible load predictions are
reported as errors, not silently replaced by unconstrained estimates.

## Review and edit

- **Overview** is the default view. Before YAML generation
  it shows planned workloads; after generation it derives relationships from
  the exact rendered resources.
- **Configuration basis** lists all mechanism decisions and their reasons.
  Enabled optimizations appear below the topology; **View all decisions** opens
  the complete checklist without crowding the default view.
- **3D explorer** shows routing/model, serving and supporting-resource layers.
  Drag to orbit, right-drag to pan, and scroll or use the zoom buttons.
  **Focus selected** centers the selected component; **Reset view** fits the plan.
  These are logical layers, not physical placement.
- Both **Overview** and **3D explorer** use the same **Component inspector**.
  A serving component is selected initially when available. Click **Edit component**
  to edit its current values; selection or camera movement never changes configuration.
- **YAML** and **Download YAML** become available after resource generation.

Topology edits show the accelerator delta and hard-budget impact. The sidebar
also offers context length, memory utilization, sequence count and batch-token
limits. Runtime edits apply to all serving roles; topology edits apply to the
selected Prefill or Decode role. **Cancel** discards the pending edit.
Switching between 2D and 3D retains the selection and pending inputs.
Apply or cancel an open component edit before switching candidates or approving.
Planning activity and Manual alternatives are collapsed after generation.
**Ready to deploy?** explains the next action; technical checks are expandable,
and warnings remain visible.

**Apply revision** performs live validation, creates a new run linked to the
original, and invalidates the old YAML checks and performance evidence. Failed
edits leave the original intact. Regenerate resources before approval.
Raw YAML is read-only here: unsupported edits cannot leave an out-of-date graph
looking valid.

## Generate, check and deploy

1. Manual automatically generates/checks YAML after planning; use
   **Generate and check YAML** to retry or after changing a candidate or editing.
   Agentic starts this step explicitly. Lens uses the existing source-pinned
   renderer and verifies consistency with the selected configuration.
   Manual completion can enable prefix caching and chunked prefill only when
   their runtime flags are established by the pinned source.
   One-click generation checks retained combinations against pinned source,
   lists rejected recipes with reasons and chooses the first passing displayed
   ranking. If none pass, it preserves the recommendation, displays the failures
   and blocks deployment. Explicit candidate selection is never silently replaced.
2. Review warnings, dependencies and pending checks. Rendering does not install
   resources. Admission, readiness and workload performance remain pending.
3. Click **Confirm configuration review**, then **Approve and deploy reviewed version**.
   Approval refreshes capacity and submits the reviewed manifest through the
   common deployment lifecycle.
4. Open **Deployments** to observe readiness and failures. See
   [Manage deployments](/user-guide/deployments).

Namespace binding, registered storage mounting and other deployment-time
adaptations still follow the existing Deploy contract. A successful planning
check does not guarantee cluster admission or successful startup.

## Evidence and controlled trials

The UI distinguishes **recommendation**, **predicted performance**, a measured
candidate, and the **best verified candidate within the tested workload and
budget**. Merely appearing in a measurement ranking does not make a candidate
the winner. No result claims a global optimum.

When enabled for an Agentic plan, trial controls require another explicit action,
a fixed workload, candidate selection, resource/time/run budgets and repetitions.
Trials use the existing bounded Deploy/Evaluate executor and clean up their own
deployments. They do not automatically modify an existing deployment. Interrupted
trials retain records for explicit cleanup.

New workflow runs and revisions are persisted with their planning snapshots.
Refreshing restores the saved plan; an expired cluster session must be resolved
before further actions. Changing requirements creates another plan.

The current catalog does not establish every requested optimization or arbitrary
combination. Autoscaling, speculative decoding and mechanisms without source
evidence are shown as unknown, not invented or enabled. Real-cluster and workload
measurements remain necessary to validate the final deployment.
